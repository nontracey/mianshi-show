# ADR · 关键取舍记录

> 格式：背景 → 决定 → 代价。每条都可被面试官追问到底（判据层，不是口号）。

## ADR-1 · 为什么 MCP 服务端用 Java + spring-ai-mcp-server-webmvc，而不是继续 Dart

**背景**：客户端 Agent 运行时在 `lib/coach/`（纯 Dart）。工具服务需要常驻进程、被任意 MCP 客户端（WorkBuddy / OpenCode / Cursor）连接；公司 AI 平台 lyra-ai 的 MCP 接入正是 `spring-ai-starter-mcp-server-webmvc:1.1.0-M3`（`build.gradle:57`、`application.yaml:44`，stateless 模式）。

**决定**：服务端用 Java 21 + 同款 starter。

**代价与收益**：放弃了"全栈一种语言"的整洁，换来两件事——① 与拆解对象同栈，生产用法（含其短板）可直接对照；② Java 岗面试官能直接读懂这条 AI 经验，消除"Dart 经验迁移不过来"的疑虑。

## ADR-2 · 为什么每个工具强制幂等键 + 超时 + 权限作用域

**背景**：lyra-ai 的 MCP 工具注册三处裸奔：无超时、无重试、无权限校验；且控制器只是表 CRUD，与注册工具脱钩。

**决定**：工具契约三件套是合入的硬门槛——没有幂等键的工具不允许有写语义；没有超时的工具不允许注册；权限作用域在 manifest 里声明，代码与声明不一致视为缺陷（CI 校验）。

**代价**：每个工具多写一层治理代码（约 1/3 工作量）。收益：任何工具失败都不静默——超时算失败、失败进审计、审计可回放。

## ADR-3 · 为什么 Skill 内容变更后必须重扫才可调用（漂移检测）

**背景**：skill/工具声明是文本，运行期可能被改动（人或 agent 自己改）。阿里云在龙蜥 SkillHub 工作坊披露的同题结论：hook 层拦截会被 agent 绕过（agent 会去读 skill 文本自己执行），治理必须下沉到工具/系统层；且 skill 供应链需要版本不可变 + 漂移检测。

**决定**：manifest 每次变更生成新版本，版本历史不可变；调用时校验当前内容哈希与已签版本一致，不一致即拒绝调用，直到重扫通过。

**代价**：多一次哈希校验与重扫流程。收益：被注入或误改的内容在调用前被拦住，而不是执行后才发现。

## ADR-4 · 为什么评测用"对照组 + 三维分"，不用端到端准确率

**背景**：只报"答对了多少题"无法定位退化来源，且样本小的时候端到端指标噪声大。

**决定**：同一题集跑两组（带工具 / 不带工具），出三个维度——功能分（契约是否满足）、增益分（带工具相对基线的增量）、安全分（执行轨迹里有无高风险事件）；结论附证据链、前提条件与置信度分级（证据不全置信度降级）。判官类评分必须是确定性规则，同一输入两次跑分必须一致（模型当判官试过，复现不了，弃）。

**代价**：每组改动都要跑双份。收益：能回答"这个工具有没有用、坏在哪、敢不敢合入"。

## ADR-5 · 为什么多租户只做设计文档，不做实现

**背景**：个人子系统没有真实多租户流量；但租户隔离是联众生产系统里真实做过的事（20+ 租户、标准下发/知识推送链路）。

**决定**：本仓库只落地单租户实现 + 一份多租户隔离设计文档（schema/作用域/审计归属，沿用联众经验）。不在没有真实需求时堆多租户代码。

**代价**：被问"支持多租户吗"只能答"单租户实现 + 隔离设计已文档化"。收益：不把设计讲成上线，归属干净。

## ADR-6 · 红线：不使用联众框架与代码（2026-09-22 用户裁定）

**背景**：本项目的叙事核心是"对照 lyra-ai 拆解、逐条补短板"。对照物是前雇主的生产系统，其代码与框架属于公司资产。

**决定**：lyra-ai 只作为**机制参照**——引用拆解结论（机制描述 + `file:line`，见 `联众AI拆解/`）来说明"企业系统在这里裸奔、我在这里补齐"；实现代码 100% 原创，第三方只允许开源组件（spring-ai、pgvector 等）。不搬运、不转译、不改名复用联众代码；配置与工程结构也不照抄。

**代价**：不能"抄近路"，部分实现要从头写。收益：归属干净——"拆过"与"做过"两条线（D12）互不污染，且对照叙事在法律与诚信上都没有瑕疵。

## ADR-7 · 交付物必须同时包含"做得好的"与"做得不好的"

**背景**：防守稿与面试叙事最容易犯的错是把个人项目讲成全优点——追问的第一个入口恰恰是短板。

**决定**：① 每个 ADR 附"已知短板"小节（如：ToolRegistry 目前无并发注册冲突处理、漂移重扫未做性能预算、评测集样本小）；② 对照组评测报告必须含 bad case 与未达标维度；③ 产出同步进 `面试防守稿/03`（MCP 防御问答），**短板先自己说**——这是把"个人项目不可信"反转成"我知道它边界在哪"的证据（D15/D21 立场）。

**代价**：文档工作量增加。收益：可追问深度提升一档，正好落在 D2 的 L2/L3 计分区。
